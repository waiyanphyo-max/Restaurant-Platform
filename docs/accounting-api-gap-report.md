# M7 accounting contract audit and M8 implementation boundary

Audit date: 2026-11-02. Scope: checked-in Spring Boot controllers, services, repositories, entities, DTOs, Supabase migration history, and shared TypeScript clients. This is a source audit; it does not assert that a remote database has these migrations or that a live API was exercised. No migrations were created or applied for M7.

The backend supports operational order snapshots, payment collection, and a daily operations report. It does **not** currently support an accounting ledger, reliable accounting revenue/profit, purchasing, expenses, reconciliation, suppliers/payables, or accounting audit trails. All `/accounting/**` contracts below are **proposals for M8**, with no working client methods or simulated success in M7. M9 should reuse M8's implemented modules and contracts.

## Accounting semantics and known integrity gaps

1. **Sales versus collected payments.** Existing `orderAmountExcludingCancelled` includes pending/uncompleted/unpaid orders created in the day and includes delivery fee/discount in `total_amount`. It is an operational booked-order amount, not recognized revenue. Existing `paidAmount` counts payments currently `PAID` with `paid_at` in that day, even if the order was created earlier or is now cancelled. Example: an order created on November 1 and paid on November 2 appears in different daily aggregates. Never add the two amounts. M8 must adopt a versioned recognition policy (including completion, discounts, delivery fee, taxes if introduced, and returns), record recognized events, and distinguish collections from revenue.
2. **Cash versus non-cash.** `CASH_AT_COUNTER` and `CASH_ON_DELIVERY` are cash methods; `ONLINE` is permitted by the schema but has no implemented payment-provider workflow. The daily payment query does not group methods. A paid COD record is driver collection, not automatically cash deposited in the restaurant till. Cashbook requires per-account custody, transfer records and settlement rules; transfers between internal accounts must not become revenue or expense.
3. **Purchase versus operating expense.** A purchase records goods acquired and creates an obligation when posted. An operating expense records rent/salary/utilities/transport/packaging/maintenance/other cost incurred. Catalog names alone cannot classify stock versus consumed supplies; persist a classification/accounting policy. A purchase settlement is a cash outflow, not a second expense. Supplier payments and expense payments must remain distinct, linked records to prevent duplicate reporting.
4. **Purchase expenditure versus COGS.** Money spent shopping is not automatically the cost of goods sold in the same period. Product stock quantity is not an inventory valuation or recipe-consumption ledger. There are no purchase cost layers, recipe yields, waste/spoilage, opening/closing inventory valuations, or cost-of-sale records. M8 may report purchases and cash flow first; it must return P&L `UNAVAILABLE` with reasons until a chosen costing method and complete valuation data support the period. Never label `paidAmount - purchases - expenses` as profit.
5. **Refunds.** `REFUNDED` exists as a payment state but no refund workflow exists. A query that counts only current `PAID` rows can change a past day's result when a row later changes state; it has no dated refund outflow to place in the refund day's report. Add refund events linked to original payment/sale, amount, cash/non-cash method, actor, reason, timestamp, status and reversals. Support bounded partial refunds and allocation to returned lines/discount/tax where relevant; total net refunds cannot exceed collected amount. Never infer a refund merely from cancelled order status.
6. **Cancellations.** Order cancellation is a workflow decision; refund is movement of previously collected money. Preserve cancelled orders and original snapshots. Customer cancellation behavior and manager cancellation behavior currently differ as described above. Establish one transactional policy for unpaid payment cancellation, stock release, paid-order credit/refund requirements and audit across all entry points, including delivery cancellation. Reports must retain the cancellation event's effective date and avoid rewriting prior closed periods silently.
7. **Timezone/date boundaries.** Existing daily reports use `restaurant_settings.timezone` (blank fallback `Asia/Yangon`), `LocalDate.atStartOfDay(zone)` and the half-open next-local-midnight window. Missing settings/invalid zone fail; future local report dates fail. M8 must retain half-open `[startAt,endAt)` intervals, using IANA local calendar days/months/years, including DST-length days. Do not use device timezone, UTC date slicing, fixed 24-hour arithmetic, or the client's timezone as authority. Return resolved timezone/window. Currency/timezone changes need effective dating or a controlled lock after financial posting; otherwise old periods can be relabeled/rebucketed. Preserve UTC/offset instants plus effective local accounting date and policy version on posted records.
8. **Historical prices and identities.** Existing line and modifier name/price snapshots are useful and should be reused. Order-level discount exists, but tax and line discount allocation snapshots do not. New purchase item names, units, unit costs, supplier identity, currency/scale, authorized actor display/role-at-event and refund allocations need snapshots. Actor UUID nullable after profile deletion does not prove a historical staff name; do not join the current profile and imply it was the historical value. New actors always derive from the authenticated server context, never from a request body.
9. **Monetary precision.** Existing money is PostgreSQL `BIGINT`, Java `Long`/`long`, JSON numeric fields; currency is a mutable restaurant setting with no per-order scale snapshot. The source does not establish a universal minor-unit convention, so M7 must not divide all values by 100 or infer scale from device locale. JavaScript numbers cannot exactly represent every 64-bit integer, and aggregate sums can exceed safe bounds even if each order is small. Proposed contracts use integer **strings** plus explicit `currency`/`scale`; fractional quantity uses decimal strings and server `BigDecimal`/PostgreSQL `NUMERIC`, never binary floats. Validate nonnegative input where appropriate, currency/scale agreement, precision bounds, multiplication rounding and totals server-side. Preserve signed values for report adjustments. A forward migration/backfill must explicitly approve legacy currency/scale before converting; do not guess historical units.
10. **Tenant isolation.** The branded build ID is a client restriction, not authorization proof. Spring checks the validated JWT UUID's current membership for every operation and scopes record lookup to the same route restaurant. Existing order/items/modifiers use tenant-scoped queries and composite FKs; payments/history inherit tenant through their parent. New tables need mandatory `restaurant_id`, compound uniqueness/FKs for supplier/catalog/purchase/payment/account/audit references, scoped repository methods and exports, and transactional ownership validation. Receipt upload/download must use a private storage namespace and a tenant-checked server route or short-lived URL. No service-role key, database credential or cross-tenant response cache belongs in Expo.
11. **Owner/Manager permission enforcement.** `REPORT_READ` is currently OWNER/MANAGER; `ORDER_READ` and `PAYMENT_READ` also belong to STAFF for operational duties; driver access is assigned-delivery constrained. Do not use those broad operational permissions as authorization for accounting. There are no current accounting permission constants. Add explicit accounting read/write/close/export/correct/audit permissions to Spring and explicitly grant the intended ones to MANAGER; OWNER currently receives all enum values, MANAGER only the listed values. Every endpoint and attachment/export path requires server checks. Frontend audience filtering is only presentation. Staff/Driver must never receive accounting report data through hidden routes, eager requests, cache reuse or exports.

## Proposed M8 REST contracts — not implemented

Base prefix for **every route in this section**: `/api/v1/restaurants/{restaurantId}/accounting`. Types are `Proposed*` exports from [contracts.ts](../apps/operations-mobile/src/features/accounting/contracts.ts). M7 does not call these routes. New capability responses and permissions require backend implementation before any gate is enabled.

Common proposed rules:

- JWT and same-restaurant membership are mandatory. Proposed permissions `ACCOUNTING_READ`, `ACCOUNTING_WRITE`, `ACCOUNTING_CLOSE`, `ACCOUNTING_CORRECT`, `ACCOUNTING_EXPORT`, `ACCOUNTING_AUDIT_READ` are **not** current enum values. Only OWNER/MANAGER receive the appropriate grants in M8. Read permissions do not imply corrections or export permissions.
- Server derives restaurant, actor, monetary totals, allocations, effective permissions and timezone. Request bodies cannot choose actor/tenant or directly set `amountPaid`, `outstanding`, `paidAmount`, computed cash balance or audit stamps.
- `fromDate` is inclusive, `toDate` exclusive, both `YYYY-MM-DD` in restaurant timezone; responses return `ProposedPeriod` with resolved instants. Calendar-month/year pickers translate to the first day and next month's/year's first day. For single-day shopping use the corresponding local day. Validate bounded ranges and known filters.
- Proposed list contracts return `ProposedPage<T>`, with opaque cursor and stable descending event-time/id ordering; `limit` defaults 20, maximum 100. `search` is a bounded, trimmed text query, not SQL. Financial totals come from a separate complete aggregate, never the currently loaded page. `granularity=DAY|MONTH|YEAR` is accepted only by summary/report routes.
- Creation and monetary writes require an `Idempotency-Key` scoped by tenant, actor, route and request hash; replay returns the original result, mismatched reuse is 409. Updates/corrections require `expectedVersion` with optimistic locking. Create returns 201, reads/updates 200; errors use the existing JSON API error envelope. No silent retry of a financial write without its stable idempotency key.
- Posted financial records are immutable. Update routes may edit drafts/catalog metadata; correcting a posted record appends a reversal/correction linked to the original with mandatory reason and server timestamp. Closed periods require an explicit correction operation. Never erase history with DELETE.

## M8 acceptance gates and M9 reuse

M8 should implement backend semantics and permission tests first, then activate modules one at a time through real capabilities. Both OWNER and MANAGER use the same feature components/services; route visibility also requires the verified role and effective server permission. No empty accounting page should claim that missing data is zero.

- **Authorization:** missing/expired JWT, wrong restaurant, removed membership, unrecognized role, STAFF/DRIVER direct URL/API access, forged actor IDs, cross-tenant supplier/item/payment/receipt/export IDs all fail. Driver operational payment effects do not grant accounting read. Test every new read/write/export path.
- **Historical integrity:** menu/supplier/member changes leave old price/name/unit/actor snapshots intact; cancellation and refund are separate; partial refunds and paid cancellation preserve original collections and dated reversals; repeated submissions do not double-post.
- **Precision and periods:** values beyond JavaScript safe integer range stay exact, decimal quantities round per policy, mixed currency/scale is rejected, date/month/year and DST boundaries are correct, UTC/device date cannot alter restaurant-local reports, and closed periods cannot mutate silently.
- **Purchases/payables:** persistent inactive catalog search/reactivation, seven-day cutoff including never-purchased items, purchase line snapshots, full/partial supplier payments, concurrent allocations and reversals reconcile. Receipt uploads/downloads are tenant-private.
- **Cash:** opening + receipts − payouts equals expected closing; actual − expected equals difference; cash/non-cash separated; COD handover never duplicates income; daily close locks consistently against concurrent movements and correction history is retained.
- **Reporting:** totals represent all matching records, not a page; purchases and payments/expenses are separated; unavailable COGS/recognition returns P&L unavailable; CSV matches the authorized period and neutralizes spreadsheet formulas.
- **Reuse:** M9 imports the implemented M8 feature modules and contracts; do not clone a second shopping, supplier, financial report, or audit ledger. Replace proposed DTOs only after an implemented versioned backend contract and integration evidence exist.

M7 validation and remaining native/provider setup are recorded separately in [m7-acceptance.md](m7-acceptance.md). The current backend [daily report tests](../app/api/src/test/java/com/restaurant/platform/service/RestaurantReportServiceTest.java) verify operational aggregation/local-day behavior; passing them does not establish accounting accuracy.
