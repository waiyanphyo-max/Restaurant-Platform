### Approved runtime refresh contract, not implemented in D0

- Backend remains the sole editable runtime authority. A future public brand view exposes only safe display name, logo, validated colors and revision; no private settings, membership, finance, QR credentials or secrets. No new URL, schema, exact TTL or permission enum is selected here.
- Successful palette/logo/catalog saves invalidate the appropriate same-restaurant views. Guest refresh/reload and native launch/foreground/bounded refresh load that tenant's current runtime data without a new APK. A stale version requires conflict review; failed saves keep the previous persisted value and do not report success.
- Cache identity includes the fixed restaurant and relevant environment/session boundaries. Abort/discard obsolete private queries on account, membership or tenant-scope changes. Offline branding may use only the last validated same-tenant theme or reviewed embedded fallback. A retry must never select another restaurant or submit a second order/payment.
- The current transport's `cache: "no-store"` is not an automatic runtime-theme mechanism. Current native hooks provide scoped in-memory query state/manual reload, not versioned theme synchronization. UXI-02 defines the contract; UXI-03/06/07/08 integrate it.

Current evidence: [transport.ts](../packages/api-client/src/transport.ts), [Customer useApiQuery.ts](../apps/customer-mobile/src/hooks/useApiQuery.ts), [Operations useApiQuery.ts](../apps/operations-mobile/src/hooks/useApiQuery.ts).

## 5. Workflow preservation contract

- **Authorization and tenancy:** retain Spring membership/role/ownership enforcement, fixed native UUID/app/environment/origin checks, trusted Guest tenant resolution, Customer subject ownership and assigned-driver privacy/revalidation. UI visibility never grants access. Owner/Manager retain catalog/settings grants; preserve actual Staff permissions, Owner-only team/ownership and Owner-only logo upload.
- **Guest and Customer ordering:** retain account-free Table/Common QR distinction, read-only browse without valid QR, private `#qrToken` handling and `X-Queue-Token`, embedded cart/receipt states, exact body/key replay and recovery limits. Preserve Customer server quote/fees/stock, COD rules, durable checkout-attempt identity, owned cancellation via `canCancel` and current-price reorder. Do not imply ordinary carts/address drafts survive process death.
- **Operations:** use existing `POST /orders/{orderId}/actions`, server `availableActions`, `expectedStatus` and `409 ORDER_ACTION_STALE`; retain meaningful trimmed 10–500-character cancellation reasons. Staff early unpaid PENDING/ACCEPTED cancellation differs from Owner/Manager's full grant; paid/settled cancellation stays rejected. Keep stock disposition, actor/history and payment independence. Kitchen Complete → READY for delivery/queue is separate from physical pickup, delivery and explicit COD cash confirmation; eligible nonqueue fulfillment can complete while unpaid. Default-driver configuration requires eligible `DELIVERY_DRIVER`; manual assignment retains its separate broader eligible-member policy.
- **Accounting:** retain exact whole-currency decimal strings, immutable originals/audit/reversal chains, stable financial request keys and uncertain-result reconciliation; restaurant-local DAY/MONTH/YEAR/RANGE up to 366 inclusive days; current daily/monthly sales trends/charts and bounded private CSV exports. Distinguish order-cohort net sales (which can include unpaid orders), dated collections, refunds and physical cash. COGS/profit stays null when unsupported. Ledger order count is not CSV physical-row count.
- **Shopping/Purchasing:** shopping plans contain item/quantity/unit and create no financial posting. Actual purchases create obligations; settlements/payments remain separate, with existing durable purchase-attempt recovery. No new accounting engine, provider refund, automatic recurring posting, tax/till custody or invented role.
