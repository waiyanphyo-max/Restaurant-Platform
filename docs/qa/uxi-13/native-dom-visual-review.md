22 November 2026, Asia/Bangkok. Reviewed saved current Figma references and fresh browser screenshots using `view_image`, inspected the preview adapters and actual navigation source, and executed a separate synthetic headless-Chrome scroll/focus probe. No product source, native identity, Figma or business records were changed.

**Disposition: partial visual evidence, no native or pixel acceptance.** The evidence supports the observed static layout, readable fallback states and scroll reachability. It leaves design differences, browser focus-scroll behavior and native accessibility for explicit review.

- Root's [56 measurement rows](native-dom-results.json): 27 English and 29 Burmese-document cases; zero document-width overflow and zero unnamed visible controls. That aggregate alone cannot detect clipped content inside an overflow container.
- Additional [scroll/focus results](native-dom-scroll-results.json), [runner](native-dom-scroll-check.cjs) and execution log `native-dom-scroll-check.log`: 22 representative cases. Four screen families (Home, address-stage Checkout, Dashboard and Financial Summary) cover **both A English and B Burmese/mixed-language at both 100% and 200%**. Product, final quote/review and daily closing add A100/B200 cases. This avoids treating language and scaling as the same variable.
- The initial sandbox could not start Chrome (`DevToolsActivePort` absent). The identical isolated local synthetic probe completed with allowed browser/loopback execution; no assertion or product behavior was changed. A follow-up added explicit horizontal-scroll measurement, and another added the matching final quote state for C04. The final retained run contains all 22 cases.

These previews render actual screen/shared-shell TSX through React DOM SSR with synthetic providers. `scripts/customer-preview.cjs` and `scripts/operations-preview.cjs` substitute native components with HTML. Their style adapters multiply explicit `fontSize` and `lineHeight` by the fixture's 1×/2× font scale, and `useWindowDimensions().fontScale` drives native navigation minimum widths. Thus the root JSON's `rootTextScale: 1` does not mean its generated “200%” fixture text was unscaled; scaling is already in the generated pixel styles. This remains an approximation of Android text scaling.

The adapters force text `white-space: pre-wrap` / `overflow-wrap: anywhere`, approximate flexbox and native ScrollViews with CSS overflow, replace SafeAreaView/KeyboardAvoidingView with plain views and do not run screen effects or touch callbacks. They use Arial / Windows Myanmar Text fallback, not verified native Inter/Padauk fonts. Header/footer differences, word breaking, focus and scrollbar behavior therefore need native confirmation. Browser viewport sizes here are 360×1000 Customer and 320×1000 Operations; the saved Figma specimens are 390×844. No pixel-equivalence score is justified.

## Wrapping, clipping and scroll reachability

At 100%, the long English restaurant and product names wrap without observed glyph clipping. Burmese glyphs render in the observed Windows fallback at both sizes. At 200%, headings and long words span multiple lines; Settings' “Restaurant” even breaks mid-word in the DOM adapter. This preserves content in the available width, with a considerable increase in scrolling. English Operations headings and finance text remain visible in the Burmese-document cases: these are mixed-language screens, not evidence of complete Burmese localization or linguistic approval.

Content partly cut off at the top/bottom of a screenshot lies at the boundary of a scrollable viewport. The supplemental probe verified the underlying content rather than labelling every viewport crop a layout defect:

| Additional check | Actual result | Limit |
| --- | --- | --- |
| Document width across 22 cases | 22/22 equals viewport, no document-width overflow | Body uses overflow hidden; nested scrolling must be checked independently |
| Main-content controls after nearest scrolling | 140 enabled control occurrences examined; zero not fully revealed | Static buttons/read-only inputs; disabled controls and tabs assessed separately; no action fired |
| Vertical main-content scrolling | Every selected page scrolls to its lower content; final cart, checkout confirmation, refresh and closing-reversal actions remain reachable | Does not simulate Android gestures, keyboard avoidance or TalkBack scrolling |
| Last navigation tab via real browser Tab-key traversal | 22/22 last tabs receive focus in expected source order | Focus is not equivalent to full visual reveal |
| Full last-tab reveal by browser focus autoscroll | 14/22 fully revealed; 8 Customer cases partially clipped | Explicit remaining DOM focus-scroll difference, described below |
| Full last-tab reveal after explicit horizontal scroll to end | 22/22 fully visible | Establishes scroll reachability only; native focus behavior remains unverified |

Both actual app shell files intentionally use a horizontal `ScrollView` with a tab minimum width of `64 × max(1,fontScale)`. At 200%, a 128-unit tab cannot keep all four/five destinations visible inside a 320/360-unit viewport. The screenshots' horizontal navigation scrollbar and initially offscreen right-hand destinations are consistent with that source contract, not hidden/discarded destinations.

Operations autoscroll fully revealed More at both sizes. Customer's Account tab received keyboard focus but Chrome left its right edge about **5 px outside the nav at Burmese100**, **16 px at English200**, and **24 px at Burmese200**. Eight of the 22 measured case occurrences show this. Explicit scrolling to the nav's end fully reveals the entire tab in all cases, including Burmese200. Compare [B200 keyboard focus](screenshots/scroll-customer-b-home-360-200-keyboard-focus.png) with [B200 after explicit end-scroll](screenshots/scroll-customer-b-home-360-200-bottom.png). This is a real limitation of the observed DOM presentation and prevents an unqualified keyboard-focus/reflow PASS. It does **not** establish an Android defect: browser focus handling, CSS max-content flex sizing and the native ScrollView differ. QA/mobile owners must reproduce on an installed app with Android font scaling and TalkBack before deciding on a minimal product correction. No product source was changed on this evidence alone.

## Accessibility and state boundaries

The root AX/DOM evidence finds named controls, headings, selected tabs and disabled states in synthetic screens. The additional real Tab-key traversal reaches the final destination in all 22 cases. Main-content scroll checks reveal their enabled controls without clipping. Product lower screenshots retain a visibly disabled Add to cart while required options are incomplete; quote/review explicitly distinguishes confirmation from cash collection; daily closing retains a separate reversal review action. No final mutation or confirmation callback runs in static SSR.

No broken loaded icon image was reported in the root samples, and visible product media fallback copy is truthful. With no remote photo loaded, these fixtures do not test loading/error transitions or publication bytes. Reduced-motion preference was observed by the root browser probe; static SSR cannot prove animated transition behavior. Names in DOM/AX do not prove native reading order, grouped-label announcements, focus return/confinement, live announcements or switch traversal.

Native safe areas/status bars, virtual keyboard/insets, real glyph shaping/fonts, 200% Android display/font settings, TalkBack exploration/gesture scrolling, dialogs, GPS/Maps, offline/reconnect transitions and native image behavior remain NOT RUN/BLOCKED on device/environment inputs. Static labels/source assertions and JS exports do not close those gates.
