## Remaining blockers and next actions

1. Install signed Customer and Operations builds on a device or a Google Play-enabled AVD with the matching SDK. Use a staging Spring/Supabase environment and an Android Maps key restricted to the Customer package and signing SHA-1. Verify account creation and email confirmation, saved address reload after restart, real tiles and pin drag, permission denial and grant, temporary GPS checkout, and Maps app and browser handoff. Reassign a task while Operations is backgrounded.
2. Define inventory and payment outcomes for Manager cancellation by order state, then cover cancellation with and without stock reservations. Check for and resolve existing address-default duplicates before enforcing a single default. Exercise the delayed POST across a process restart and determine how the server should handle explicit abandonment. Agree on supported recipient-phone formats.
3. Repeat the checkout-to-cash flow in staging with two customers and two restaurants. Reconcile one real staging COD collection against cashbook, sales and closing reports. Test FCM opt-in, token rotation, offline logout and account switching on a shared device. Run the skipped PostgreSQL 17 Testcontainers suite when Docker is available.
4. Keep the legacy delivery POST in the compatibility review. It has a saved-address contract and lacks M12 confirmation and idempotency. M12 validates the submitted city and township and a point for navigation. Physical presence, address-to-pin correspondence and geofence membership are outside that validation. Build attestation is absent from the restaurant-scoped API contract. [API contract](api.md#customer-delivery-checkout) · [Architecture decision](product-architecture-decision.md)

Local integration passed for the principal M12 checkout-to-cash workflow after QA-01. The open defects and unrun Android and provider checks keep full milestone integration acceptance open.

### Checkout recovery contract

`DELETE /api/v1/customer/restaurants/{restaurantId}/orders/delivery/checkout` uses the authenticated customer, the restaurant path and the `Idempotency-Key` header. A `200` returns the earlier order receipt when checkout committed first. A `204` confirms the old key cannot commit. A receipt `GET` returning `404` indicates the order was absent at the time of the lookup. The app keeps its key when the settlement response is uncertain.
