# M14 physical Android acceptance plan

This checklist is for the developer’s device run after M14. Record the build revision, device model, Android version, execution date and tester. For each row, select **Pass**, **Fail** or **Blocked** after running it and add a reference to the evidence. The fields start empty.

## Prepare the test environment

1. Use a disposable or separately authorized test backend, Supabase Auth and database. The existing single Supabase Cloud project was outside the M14 test run. Treat any testing against it as a separate developer decision. Run the write scenarios below only in an isolated environment. Apply reviewed pending migrations to the test environment in timestamp order and verify Spring starts with schema validation enabled.
2. Prepare an allowlisted Platform Admin, distinct A and B owners, a Manager, Staff member and two eligible workers for A, a B-only Operations account and two independent customer accounts. Use test mailboxes and synthetic addresses and phone numbers. Keep actor names and tenant IDs in the run sheet. Record opening stock, opening cash and the restaurant timezone. Use known prices, one tracked product with a variant and required modifier, one unavailable product, an active table, a Common QR, an active delivery zone, a delivery fee and a minimum. Provision the restaurants in D01 before resolving their branded builds, or record the pre-provisioned fixture IDs and run D01 with a separate synthetic restaurant.
3. Bind the reviewed A/B restaurant configs to the correct UUIDs, staging API and guest hosts. Configure Admin and Guest from their `.env.example` files and the approved Auth redirect URLs. Supply the public Supabase URL and publishable key to both native builds. Supply the server’s Auth issuer, JWKS URL, database access, admin allowlist and approved invitation configuration separately. Configure a stable server-only `APP_IDEMPOTENCY_ENCRYPTION_KEY` for keyed QR checkout. Confirm the Operations membership endpoint is deployed before the app is installed. [Auth setup](auth-session-setup.md) · [Guest QR runbook](m6-guest-qr-ordering.md) · [Android build runbook](m13-android-branding.md)
4. Give the phone a route to the test API and guest web. Prefer test HTTPS hosts with valid certificates. Open the guest host and Spring `/actuator/health` from the phone before installing. For a local development build, use a reviewed host address or an explicit `adb reverse tcp:8080 tcp:8080` setup with the corresponding embedded API URL and Android network configuration. `10.0.2.2` is an emulator address. Check the route again after switching between Wi-Fi and cellular.
5. Use a signed staging APK for each app and tenant. Keep each release plan, Git SHA, APK digest, app/package ID, version, fingerprint and public signing certificate fingerprint. Compare each artifact with `npm run --silent mobile:build -- verify <plan.json> <app.apk>`. Check the connection with `adb devices -l`, then run `adb -s <serial> install <app.apk>` for all four APKs. For verified HTTPS App Links, publish the matching test host statements and inspect `adb -s <serial> shell pm get-app-links <package>`. [Signing and App Links](m13-android-branding.md#signing-and-android-app-links)
6. Configure Google Maps SDK for Android for the exact Customer staging package and installed certificate SHA-1. Configure Customer FCM with the matching Android Firebase client project and package, enable the backend dispatcher with that project's server credentials and grant Android notification permission during the run. Use an additional approved Customer build with Maps omitted to check the fallback. Keep server credentials, private signing material, access tokens and QR capabilities out of captures. [Customer configuration](../apps/customer-mobile/.env.example) · [Server FCM setup](api.md#firebase-cloud-messaging-setup)

## Record the result

For each failure or blocker, capture the scenario ID, local time and timezone, build fingerprint, role, app and tenant, exact steps, expected and actual result, and whether retry/restart changed the outcome. Capture a redacted screenshot or short video, relevant app-process `adb logcat`, sanitized backend correlation and error codes, and synthetic record IDs or aggregate counts. For finance or checkout, attach before/after stock, payment, cash movement and closing counts. For provider failures, record project or app labels and the provider error category. Keep any raw auth header, email link, QR token, device token, private address or signing secret out of the report.

Record each blocked test’s missing prerequisite and rerun it after that prerequisite is available. Physical-device acceptance is complete only after the required scenarios have real-device evidence and any failures have a recorded disposition.
