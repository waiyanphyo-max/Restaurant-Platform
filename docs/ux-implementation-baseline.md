## 1. Outcome, authority and boundaries

The implementation baseline is **`5a898e5c3a383d90f87ac26a5c34d56914d39e39`**, on local branch **`uxi/00-baseline-audit`**. Current Guest, Customer, Operations and minimum API contracts already implement substantial behavior represented in Figma. UX-01 should preserve those contracts and adapt presentation. Canonical geography, optional-map/text checkout, Accept/Complete/Cancel, year reporting, CSV export, and shopping/purchasing separation are existing committed functionality.

This milestone adds only this document, within the requested documentation scope. No functional code, business logic, configuration, assets, SQL, Figma design, deployment or database records were changed. No checkout, reset, commit, push, migration, upload or QR rotation was performed. Platform Admin redesign is excluded; its existing branding metadata and callback contracts were inspected only where necessary to understand shared dependencies.

Classification:

- **KEEP**: preserve existing behavior, authorization, state, validation, pricing and data history. It does not certify pixel equality with Figma.
- **ADAPT**: supported behavior needs visual, information hierarchy, navigation, copy or accessibility work.
- **ADD**: a verified requirement lacks a corresponding implementation or contract. Product/domain/schema decisions precede implementation where indicated.
- **Design fit**: “behavior supported” means source evidence supports the intent; “partial” identifies a gap/conflict. No running-app comparison or installed-device acceptance was performed, so full visual compliance is **unverified for every screen**.

The screen appendix resolves each verified Figma frame to a route/code group. Each group specifies current status, proposed files, API/permission, risk, tests and decisions; those fields apply to every frame assigned to it. Finding IDs and screen IDs occupy different namespaces: for example, audit finding `O09` concerns finance filters, while screen `O09` is queue pickup.

Path convention: shortened backend source references such as `dto/menu/MenuProductDto.java`, `service/ManagerOrderService.java`, `entity/Product.java` and `security/RestaurantRole.java` are relative to **`app/api/src/main/java/com/restaurant/platform/`**. An app row's shortened `src/` or `app/` path inherits the explicitly named app root in that row; bare adjacent filenames inherit the preceding directory. These are path abbreviations, not alternate files.

### 4.6 QR, table, common and browsing modes

Guest browsing without a valid QR is read-only. Common QR entry is the restaurant root with `view=customer-pickup` and private `#qrToken=...`; it creates TAKEAWAY / COMMON_QR plus a daily queue ticket. Table QR entry is `/workspace` with `view=table-order` and private fragment; it creates DINE_IN / TABLE_QR and table receipt, without a queue ticket. Reviewed local `/r/[slug]` equivalents are present. These are verified in `src/lib/legacy-route.ts`, `qr-fragment.ts`, `GuestSession.tsx`, `GuestOrdering.tsx` and server `OrderService.java:670–922`.

Do not turn these design states into new conflicting cart/receipt URLs by assumption. Cart/checkout/receipt are currently embedded GuestOrdering states. Preserve host routing, alias restrictions, printed links, fragment cleanup and capability validation. `POST .../qr-context` already validates tenant/settings/token/kind/table. Queue reads use `X-Queue-Token`, never a bearer token or public URL token. Guest needs no account or delivery address. Kitchen actions belong in Operations.

Guest pending body/key is in sessionStorage without capability secrets; recovery after reload requires the original scan and stops after the existing 23-hour limit. Receipt/queue token and ordinary cart have memory limits. Customer cart/address form drafts are session/component memory; checkout-attempt identity has dedicated durable SecureStore recovery. Figma S03/S36 wording that edits are “kept” must be bounded to actual lifetime. **Do not promise durable offline cart/address storage or resurrect a lost queue token.** New durable draft storage is conditional ADD; ambiguous checkout recovery must stay intact.

### 4.7 Accounting, exports and periods

These capabilities are already committed:

- Operations `FinancialPeriodFields.tsx:8` offers DAY, MONTH, YEAR, RANGE; `financial-period.ts:27` translates Year to Jan 1–Dec 31 and enforces at most 366 inclusive calendar days. Backend `AccountingSupport.java:65` converts restaurant-local inclusive dates into a half-open timestamp interval. Device timezone and Bangkok audit timezone must not replace restaurant timezone (Figma examples use Asia/Yangon +06:30).
- `ExportReportsScreen.tsx:52` supports sales history, purchase history and financial summary CSV. `AccountingCsvAction.tsx` binds authorization/session/restaurant/focus/app activity and aborts obsolete work. `accounting-csv-file.ts` supports browser download/native sharing, private cache and timed cleanup. Export covers the filtered bounded result, independently of the current page.
- Exact whole currency is transported as base-10 strings; purchase quantities may be fractional, financial totals must remain exact. No JS floating-point money conversions.
- Order-cohort net sales, dated collections, receivables, refunds/reversals and payment flows are distinct. Net sales can include unpaid orders. Cancellation may restate cohort totals; original history remains. Refunds do not reopen receivables.
- Shopping sheets are nonfinancial plans; purchase posting creates obligations; payments are separate. Purchasing has durable exact-request recovery. No automatic recurring-expense posting.
- Cashbook is consolidated physical restaurant cash including driver-held amounts, not digital balance or per-till custody. Sequential closings, missing-input guards, newest-first reversal chains, closed-date controls, reasons, stable request keys and immutable originals remain.
- `costOfGoodsSold`, `grossProfit`, `netOperatingProfit` remain **null**, not zero. Trading payment net is not profit. No inventory valuation, double-entry/trial balance, bank reconciliation, online refund processing or period-close ledger is implied.

Figma O33/O66 correctly separate cash and sales, but “Recognized sales” needs alignment with the actual order-cohort measure. Existing `accounting/SalesDtos.java:18` already supplies daily/monthly sales trends (gross/discount/net sales, orders, products sold), and Operations `SalesDashboardPanel.tsx:60` already renders trend tables and monthly net-sales/order-count charts: **KEEP/ADAPT these**. O66's five-bar chart is explicitly fictional; an additional collection/cash-versus-sales series or unsupported aggregation lacks a matching Trend field. O34/O67's exact export-columns/CSV-row-count preview is not supplied by a dedicated preview/schema endpoint. Ledger `totalElements` counts orders, not physical CSV rows; CSV expands item lines and separately limits 5,000 orders/20,000 lines. A preview must reflect actual authorized headers and distinguish these counts. Day/month/year/range, existing trends/charts and CSV should be **KEEP/ADAPT**, not reimplemented as ADD. Unsupported metrics/groupings, arbitrary columns, CSV row-count metadata, intraday/hour filters, XLSX/PDF, actual profit or Accountant role require separate approved scope.
