# Operations Android project

This is a separate Expo/React Native application project for Owner, Manager, Staff, and Driver workflows. It is not a marketplace app or a customer-ordering app. The build embeds one restaurant ID and public brand; there is no tenant picker.

Set `RESTAURANT_SLUG`, `MOBILE_ENV=staging|production`, and `PUBLIC_API_BASE_URL` to select a real file in [`configs/restaurants`](../../configs/restaurants/README.md). A real production build requires the restaurant's unique Operations Android application ID and approved brand assets. Missing configuration fails the build. Do not put secrets in Expo `extra` or other client configuration.

From the repository root, `npm run typecheck -w @restaurant-platform/operations-mobile`, `npm run lint -w @restaurant-platform/operations-mobile`, and `npm run test -w @restaurant-platform/operations-mobile` validate this starter. `npm run build:starter -w @restaurant-platform/operations-mobile` exports a development-only Android JavaScript bundle using the explicit fixture; it does not produce an APK. `npm run android -w @restaurant-platform/operations-mobile` generates/runs the native Android project when the Android SDK is installed and a real tenant is selected.

The production Android package and icon are selected in `app.config.js` from the real build config. This project remains independent from `apps/customer-mobile`; each restaurant receives a different Operations and Customer application ID. Backend authorization still determines which signed-in members can perform each action.

## M2 authentication boundary

Copy `.env.example` to a local ignored environment file and set only the public Supabase project URL and `sb_publishable_` key. The adapter rejects a service-role or secret key and requires HTTPS outside local Android-emulator development. It keeps the SDK session in encrypted Android SecureStore under a key scoped to the project origin, environment, product, and restaurant. `expo-secure-store` is configured as an Expo plugin so Android Auto Backup excludes encrypted session entries. The SDK process lock serializes Auth operations. A foreground listener starts Supabase token refresh and pauses it in the background; a refresh that changes the Auth UUID is rejected. Sign-in and sign-out use the official Auth SDK. `src/api.ts` binds the shared member client to the embedded restaurant and current token provider; operational screens must call `getConfiguredMembership()` before showing their workspace. The API still validates JWTs, membership, and permissions on every request. A frontend role name never grants access.

Phone/SMS OTP is disabled. Enabling it requires a configured and verified SMS provider, a backend invitation/capability contract tied to the **existing Auth UUID**, rate limits, and verified same-UUID phone-change handling. A matching phone or email string cannot create or transfer membership. See the [Supabase phone sign-in guide](https://supabase.com/docs/guides/auth/phone-login) and its [phone-change identity warning](https://supabase.com/kb/troubleshooting/unexpected-behavior-with-authupdateuser-phone-phone-linked-to-incorrect-user-id). No live SMS flow is claimed by these tests.
